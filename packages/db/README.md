# @vetkit/db

The Supabase data layer for vetkit — Postgres schema (migrations), Row-Level
Security, the cross-tenant leak test, generated types, and the typed client
factory. **One shared Supabase project**, every row isolated by `tenant_id` + RLS.

> Design: [`../../project-documentation/specs/2026-06-14-supabase-data-model.md`](../../project-documentation/specs/2026-06-14-supabase-data-model.md)
> Implementation brief: [`../../project-documentation/specs/2026-06-14-supabase-r1-research-brief.md`](../../project-documentation/specs/2026-06-14-supabase-r1-research-brief.md)

## Layout

```
supabase/
  config.toml                 # generated by `supabase init` (see Setup)
  migrations/*.sql            # hand-written, committed, applied in order
  tests/cross_tenant_leak.test.sql   # pgTAP gating leak test
src/
  schemas.ts                  # Zod value-objects (jsonb single source of truth)
  database-generated.types.ts # GENERATED by `gen:types` (do not hand-edit)
  database.types.ts           # Database type + Tables/Insert/Update helpers
  client.ts                   # createAnonClient / createServiceRoleClient
  index.ts
```

## Required env (in `apps/web/.env.local`, gitignored)

```bash
NEXT_PUBLIC_SUPABASE_URL=https://<ref>.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=...   # publishable (or legacy anon) key
SUPABASE_SERVICE_ROLE_KEY=...              # SERVER ONLY — bypasses RLS
SUPABASE_PROJECT_REF=<ref>                 # for gen:types / link
# Migration-only (not app runtime): SUPABASE_ACCESS_TOKEN, SUPABASE_DB_PASSWORD
```

## Setup (one-time, after `pnpm install`)

```bash
# 1. generate config.toml for the pinned CLI version (keeps existing migrations)
pnpm --filter @vetkit/db exec supabase init

# 2. link to the cloud project (needs SUPABASE_ACCESS_TOKEN + SUPABASE_DB_PASSWORD)
pnpm --filter @vetkit/db db:link        # supabase link --project-ref $SUPABASE_PROJECT_REF
```

## Apply migrations to the cloud project (no Docker)

```bash
pnpm --filter @vetkit/db db:push:dry    # ALWAYS dry-run first — hits the real DB
pnpm --filter @vetkit/db db:push
```

## Generate types (after migrations are applied)

```bash
pnpm --filter @vetkit/db gen:types      # -> src/database-generated.types.ts
```

### After first `gen:types` — apply the jsonb override

Once real generated types exist, refine `src/database.types.ts` to narrow the
jsonb value-objects (currently typed as the broad `Json`). Replace the
`export type Database = DatabaseGenerated;` line with:

```ts
import type { MergeDeep } from 'type-fest';
import type {
  Cta,
  Contact,
  Address,
  OpeningHours,
  SocialLinks,
  Seo,
  EmergencyBanner,
  TiptapDoc,
} from './schemas';

export type Database = MergeDeep<
  DatabaseGenerated,
  {
    public: {
      Tables: {
        site_settings: {
          Row: {
            contact: Contact | null;
            address: Address | null;
            opening_hours: OpeningHours | null;
            social_links: SocialLinks | null;
            emergency_banner: EmergencyBanner | null;
            footer_links: Cta[] | null;
            default_seo: Seo | null;
          };
        };
        hero_slides: { Row: { cta: Cta | null } };
        services: { Row: { description: TiptapDoc | null } };
        faqs: { Row: { answer: TiptapDoc | null } };
        blog_posts: { Row: { body: TiptapDoc | null } };
        team_members: { Row: { bio: TiptapDoc | null; social_links: SocialLinks | null } };
        pages: { Row: { body: TiptapDoc | null; cta_buttons: Cta[] | null } };
        testimonials: { Row: { content: TiptapDoc | null } };
      };
    };
  }
>;
```

(Add matching `Insert`/`Update` overrides if the admin needs typed writes for those columns.)

## Run the leak test (CI gate; needs Docker on the runner)

`supabase test db` resets the DB each run, so the basejump test helpers must be
bootstrapped by a setup file the runner applies first (a one-off `dbdev.install`
does not persist). The full Supabase-documented chain:

```sql
-- supabase/tests/000-setup.sql (runs before *.test.sql)
create extension if not exists http with schema extensions;
create extension if not exists pg_tle;
drop extension if exists "supabase-dbdev";
select pgtle.install_extension('supabase-dbdev', resp.contents ->> 'version', 'PostgREST data dev tools',
  resp.contents ->> 'sql')
from http_get('https://api.database.dev/rest/v1/...') x, lateral (select ((x.content)::json -> 0)) resp(contents);
create extension "supabase-dbdev";
select dbdev.install('basejump-supabase_test_helpers');
```

> ⚠️ The exact dbdev bootstrap is environment-specific — confirm against the
> current Supabase "Advanced pgTAP Testing" docs when wiring CI (R10). Locally
> this needs Docker (`supabase start`), which is not installed here; the live
> `rls-smoke` (Node, no Docker) is the interim behavioral check.

```bash
pnpm --filter @vetkit/db db:test        # supabase test db (starts the local stack)
```

The test (16 assertions) proves: a clinic user reads/writes only its tenant, sees
zero of another tenant's rows and cannot insert/update into it; anon reads only
published rows, can submit a lead but cannot read leads or write content; a
platform admin sees and writes every tenant; an authenticated non-member sees nothing.
