## 1. Migration + cloud-apply workflow

### 1.1 File layout (canonical) 🏠 + ✅

Supabase lives inside the new workspace package. The CLI's `supabase/` folder is committed.

```
packages/db/
├── package.json              # @vetkit/db
├── tsconfig.json             # extends @vetkit/config-typescript/base.json
├── eslint.config.mjs         # @vetkit/config-eslint/base
├── supabase/
│   ├── config.toml           # CLI config (committed)
│   ├── migrations/           # <UTC-timestamp>_<name>.sql — hand-written, committed
│   │   ├── 0001_..._init_extensions_and_helpers.sql
│   │   ├── 0002_..._tenancy_identity.sql
│   │   ├── 0003_..._content_tables.sql
│   │   ├── 0004_..._rls_policies.sql
│   │   └── ...
│   └── tests/                # pgTAP cross-tenant leak test (see §4)
│       └── cross_tenant_leak.test.sql
└── src/
    ├── database-generated.types.ts   # GENERATED by `supabase gen types` (committed, build input)
    ├── database.types.ts             # hand-written MergeDeep over jsonb cols (see §5)
    ├── client.ts                     # typed client factory (see §5)
    └── index.ts                      # package entry — re-exports
```

> ⚠️ **verify-before-code:** Real Supabase CLI migration filenames use a 14-digit UTC `YYYYMMDDHHMMSS` prefix (e.g. `20260614120000_init.sql`), produced by `supabase migration new`. The `0001_`-style names above are illustrative ordering only — let the CLI generate the timestamp; do not hand-name them.

### 1.2 CLI install — pinned dev dependency, never global ✅

```bash
# inside packages/db
pnpm add -D supabase@<pinned>      # pin exact version; run `pnpm view supabase version` at adoption time
pnpm exec supabase --help
```

- ✅ The CLI is installable as a project dev dependency and run via the package runner; Node 20+ required (repo requires `>=20.9.0` 🏠). Version-pinning in `package.json` is the supported lock mechanism.
- ⚠️ **No specific 2026 "latest" version number was web-confirmed.** Pin to whatever `pnpm view supabase version` reports at implementation time. There is also a known CLI quirk (`supabase/cli#2773`) where default-bearing `text`/`uuid` id columns were emitted as REQUIRED in Insert types in some versions — another reason to pin and verify generated output.

### 1.3 Monorepo: point the CLI at `packages/db` ✅

Do **not** rely on `cd packages/db` inside Turbo tasks (Turbo runs from package roots; fragile). Use the global `--workdir` flag or `SUPABASE_WORKDIR`:

```bash
pnpm exec supabase --workdir packages/db db push --linked
# or
export SUPABASE_WORKDIR=packages/db
```

✅ `--workdir` / `SUPABASE_WORKDIR` is the documented monorepo mechanism. Run `supabase init` once inside `packages/db` to create `supabase/config.toml`.

### 1.4 Author migrations BY HAND (no-Docker constraint) ✅ + ⚠️

```bash
pnpm exec supabase migration new init_tenancy
# -> supabase/migrations/<UTC-timestamp>_init_tenancy.sql  (plain SQL, you write the DDL)
```

> ⚠️ **Central tension — confirm Docker posture with owner.** `supabase db diff` (and declarative-schema auto-generation under `supabase/schemas/`) needs the **local Docker stack**; ✅ `supabase db push` to a linked cloud project does **not**. The spec implies a cloud-only/no-Docker preference. Under that constraint, **all migrations are hand-written `.sql`** — you cannot auto-generate them with `db diff`. (The "`db diff` strictly requires Docker" claim is ⚠️ not web-confirmed this cycle; if a Docker-free auto-diff path matters, verify against the `supabase db diff` CLI reference before committing to hand-written-only.)
>
> This is fine for R1: RLS policies, GRANTs, and seed/DML must be hand-written regardless of model — the `migra` diff engine ✅ silently omits exactly those (RLS, GRANT/REVOKE, DML, comments). So declarative schemas buy nothing for the security-critical core.

### 1.5 Apply to the cloud project (no Docker) ✅

```bash
# Non-interactive (CI or scripted). All three secrets required or `link` hangs.
export SUPABASE_ACCESS_TOKEN=...        # personal access token (auth)
export SUPABASE_DB_PASSWORD=...         # the project's DB password
pnpm exec supabase --workdir packages/db link --project-ref <project-ref>
pnpm exec supabase --workdir packages/db db push --linked --dry-run   # ALWAYS dry-run first
pnpm exec supabase --workdir packages/db db push --linked
```

- ✅ `link` + `db push` provably needs **no** Docker (this is the documented CI/CD flow). `db push` applies only migrations not yet recorded in the remote `supabase_migrations.schema_migrations` table, in order.
- ✅ `db push` flags: `--linked`, `--db-url`, `-p/--password` (or `SUPABASE_DB_PASSWORD`), `--dry-run`, `--include-all`, `--include-roles`, `--include-seed`.

### 1.6 Owner credentials needed (per the shared single-project model) ⚠️

Because the spec locks **one shared Supabase project** (RLS-by-tenant, not project-per-clinic), there is **ONE** set of secrets, not N:

| Secret                  | Used for                                       | Notes                            |
| ----------------------- | ---------------------------------------------- | -------------------------------- |
| `SUPABASE_ACCESS_TOKEN` | `link` auth                                    | personal access token; CI secret |
| `SUPABASE_DB_PASSWORD`  | `link` / `db push`                             | the shared project's DB password |
| `<project-ref>`         | `link --project-ref`, `gen types --project-id` | the shared project ref           |

> ⚠️ **Owner decision:** where these live (Vercel project env vs a secrets manager) and who runs `db push` (a human, or CI on merge to `main`). The single-project model means the migration workflow does **not** loop over project-refs — confirm that's still the intent before wiring CI.

### 1.7 Commands to AVOID under cloud-only ✅

- `supabase start` / `supabase db reset` — local Docker only.
- `supabase db diff` — needs local stack; not usable for auto-generating migrations here.
- `db reset --linked` / destructive `db push` — hit the **real** cloud DB, no undo. Dry-run first, always.
- ⚠️ DDL via the **pooled** connection (port 6543, transaction mode) breaks migrations — if ever applying SQL directly, use the direct/session connection (5432) or session pooler, not the transaction pooler. `db push` handles this for you; this only bites manual SQL.

## 2. RLS recipe (the load-bearing part)

Maps spec §5 onto verified Supabase patterns. **Every table:** `alter table ... enable row level security;` → deny-by-default. ✅ `service_role` bypasses RLS entirely — never ship that key to a browser/client bundle.

### 2.1 Security-definer helpers (MANDATORY hardening) ✅

Live in a **private, non-API-exposed schema**. Each is `stable`, `security definer set search_path = ''`, and **every** object reference is schema-qualified (the empty `search_path` closes the privilege-escalation hole Supabase's `function_search_path_mutable` advisor flags; with it, an unqualified relation throws `relation does not exist` at runtime).

```sql
create schema if not exists private;

-- spec §5: auth_tenant_ids() -> setof uuid
create or replace function private.auth_tenant_ids()
returns setof uuid
language sql
stable
security definer
set search_path = ''
as $$
  select m.tenant_id
  from public.memberships m
  where m.user_id = (select auth.uid())
$$;

-- spec §5: is_platform_admin() -> bool
create or replace function private.is_platform_admin()
returns boolean
language sql
stable
security definer
set search_path = ''
as $$
  select exists (
    select 1 from public.platform_admins pa
    where pa.user_id = (select auth.uid())
  )
$$;
```

> Why `security definer` here: a policy that SELECTs from `memberships`/`platform_admins` (which themselves have RLS) directly would ✅ trigger **infinite RLS recursion** (Postgres `42P17`). The definer function runs as its owner and bypasses the inner table's RLS — the standard escape hatch.

> ⚠️ **Note vs spec:** the spec sketches these helpers without a schema qualifier; placing them in `private` (not `public`) is the ✅ web-confirmed best practice. Reference them as `private.auth_tenant_ids()` / `private.is_platform_admin()` in policies. Also wrap helper calls in a `select` (next section) for per-statement evaluation.

### 2.2 Performance wrapping (NON-NEGOTIABLE) ✅

- Wrap every auth/helper call as `(select ...)` so Postgres evaluates it **once per statement** (initPlan), not once per row. ✅ Documented 95–99.99% speedups; the unwrapped form is a silent correctness-invisible perf cliff.
  - `(select auth.uid())`, `(select private.auth_tenant_ids())`, `(select private.is_platform_admin())`.
- ✅ Add a **btree index** on every owner/tenant column referenced in a policy: `memberships(user_id)`, `memberships(tenant_id)`, and **every content table's `tenant_id`**. (Supabase benchmark: 171ms → <0.1ms.)

### 2.3 Canonical per-table policy set ✅

**Separate policy per operation** (not `for all`), each with an explicit `to` role clause. ✅ Relying on `auth.uid()` alone to exclude anon is discouraged — a policy with no `to` clause applies to **all** roles including anon. `using` filters existing rows (select/update/delete); `with check` validates new/changed rows (insert/update). UPDATE needs **both**, and a SELECT policy must also exist for UPDATE to function.

**Standard content table (e.g. `services`, `blog_posts`, `team_members`, `faqs`, `gallery_images`, `pages`, `testimonials`, `hero_slides`):**

```sql
alter table public.services enable row level security;

-- ANON (public site): published-only, read-only
create policy "services anon read published"
on public.services
for select to anon
using ( status = 'published' );

-- AUTHENTICATED (admin): own-tenant OR platform admin, full CRUD
create policy "services member select"
on public.services
for select to authenticated
using (
  tenant_id in (select private.auth_tenant_ids())
  or (select private.is_platform_admin())
);

create policy "services member insert"
on public.services
for insert to authenticated
with check (
  tenant_id in (select private.auth_tenant_ids())
  or (select private.is_platform_admin())
);

create policy "services member update"
on public.services
for update to authenticated
using (
  tenant_id in (select private.auth_tenant_ids())
  or (select private.is_platform_admin())
)
with check (
  tenant_id in (select private.auth_tenant_ids())
  or (select private.is_platform_admin())
);

create policy "services member delete"
on public.services
for delete to authenticated
using (
  tenant_id in (select private.auth_tenant_ids())
  or (select private.is_platform_admin())
);
```

> 🏠/spec note: `hero_slides` and `site_settings` are **always-live config** (no `status`). For those, the anon SELECT policy is `using (true)` (or omit the status filter) instead of `status = 'published'` — they have no draft state. Everything else (the member CRUD block) is identical.

**`media` (public-read marketing images):** anon `select using (true)`; authenticated CRUD scoped by `tenant_id` exactly as above.

**`submissions` (leads — anon writes, never anon reads):**

```sql
alter table public.submissions enable row level security;

create policy "submissions anon insert"
on public.submissions
for insert to anon
with check ( tenant_id is not null );
-- NO anon select policy → anon cannot read submissions.

create policy "submissions member select"
on public.submissions
for select to authenticated
using (
  tenant_id in (select private.auth_tenant_ids())
  or (select private.is_platform_admin())
);
-- + member update for status ('new'/'read'/'archived') with the same predicate.
```

**`tenants` / `memberships` / `platform_admins`:** SELECT for self/members + platform admin; **writes platform-admin-only** (clinics don't create tenants or grant access). Use `(select private.is_platform_admin())` in the write `with check`.

**GRANTs pair with RLS** ✅ — RLS filters rows but the role still needs table privileges:

```sql
grant select on public.services to anon;
grant select, insert, update, delete on public.services to authenticated;
-- service_role is granted implicitly; never expose its key client-side.
```

### 2.4 RLS gotchas ✅

- **Types are NOT RLS-aware.** A green `supabase gen types` typecheck does not mean a write is allowed — RLS rejects at runtime. Never treat typecheck as authorization.
- `to anon`/`to authenticated` must be **explicit** on every policy.
- INSERT predicates go in `with check`, **not** `using` (a `using` on insert is ignored).
- For the most sensitive tables, `alter table ... force row level security` makes even the table owner obey RLS (belt-and-suspenders).

> ⚠️ The spec keeps tenant correctness on the **public path** in the data layer (§6 `tenantTable` helper), not in anon RLS (anon RLS is published-only, tenant-agnostic). That is the documented residual: a crafted anon call could read another tenant's _already-public_ published content. Owner accepted this trade as low severity (all public marketing copy). The stricter alternative (service-role reads behind the `tenantTable` guard) is an R2 read-path decision, not an R1 migration concern.

## 3. Storage bucket + image-transform recipe

Maps spec §4 (`media` table + one public-read bucket, paths namespaced by `tenant_id`).

### 3.1 Create the bucket in a migration (SQL) ✅

```sql
insert into storage.buckets (id, name, public)
values ('media', 'media', true);
```

✅ Storage metadata lives in Postgres, so this is migration-safe. (The `config.toml [storage.buckets.*]` + `supabase seed buckets` path is a ⚠️ local/dev seeding convenience, not the production mechanism — use the SQL insert.)

### 3.2 Object paths + write RLS ✅

Namespace objects: `media/<tenantId>/<category>/<file>`. Public buckets are **read-open** so a SELECT policy is optional; **writes are denied by default** and must be granted, scoped by the first path segment:

```sql
create policy "media tenant uploads"
on storage.objects
for insert to authenticated
with check (
  bucket_id = 'media'
  and (storage.foldername(name))[1] in (
        select t.id::text from public.tenants t
        where t.id in (select private.auth_tenant_ids())
      )
);
-- + matching update/delete policies with the same predicate.
```

✅ Helpers: `storage.foldername(name)` → `text[]` of folder segments; `(storage.foldername(name))[1]` is the tenant segment; `storage.filename(name)`, `storage.extension(name)` also exist.

> ⚠️ Path namespacing scopes **writes/organization only** — on a public bucket, **reads are open to everyone regardless of path**. That's correct for vetkit (all marketing images are public). Never put anything sensitive in a public bucket assuming the path hides it.

### 3.3 Image transformations ✅ — **PAID-PLAN BLOCKER**

```ts
const { data } = supabase.storage.from('media').getPublicUrl(path, {
  transform: { width: 500, height: 600, resize: 'cover', quality: 80 },
  // format defaults to auto (WebP/AVIF); pass format: 'origin' to opt out
});
// -> .../storage/v1/render/image/public/media/<tenant>/...?width=500&height=600
```

- ✅ `resize ∈ cover|contain|fill` (default `cover`, crops toward geometric center); `quality 20–100` (default 80); auto WebP/AVIF unless `format: 'origin'`.
- ✅ **Transformations require Supabase Pro plan or above — they DO NOT work on Free tier.** This is a hard cost/plan decision (see §7).
- ✅ Transforms are **resize-only — no art-direction/focal crop.** The spec's `focal_x`/`focal_y` (from the `media` table) must be applied **client-side** via CSS `object-position: <x>% <y>%` on the rendered `<img>` — they cannot go in the transform URL.
- ✅ Responsive `srcset`: emit multiple `getPublicUrl(..., { transform: { width } })` URLs, or wire a custom `next/image` loader mapping `{ src, width, quality }` onto the `render/image/public/` URL.

## 4. Cross-tenant leak test (gating, ships with R1)

**Recommendation: pgTAP via `supabase test db` as the blocking CI gate** — most idiomatic, fastest, fully isolated (single rolled-back transaction, zero cleanup), tests RLS at the Postgres source of truth. ✅ The official docs explicitly say to "always test negative cases."

### 4.1 Layout + runner ✅

- Tests live in `packages/db/supabase/tests/`, created with `supabase test new <name>.test`, run with `supabase test db`. Wrapped in `begin; select plan(N); ...; select * from finish(); rollback;`.
- Impersonation uses the ✅ basejump `supabase_test_helpers` extension (third-party dbdev package). ⚠️ Docs pin version `0.0.6` — confirm it's still current at implementation time and install it **only** into the test DB, never production.

```sql
select dbdev.install('basejump-supabase_test_helpers');
create extension if not exists "basejump-supabase_test_helpers" version '0.0.6';
-- helpers: tests.create_supabase_user(email), tests.get_supabase_uid(email),
--          tests.authenticate_as(email), tests.clear_authentication(),
--          tests.rls_enabled('schema','table')
```

### 4.2 Skeleton — proves spec §5's four assertions ✅ (data adapted ⚠️)

```sql
begin;
select plan(5);

-- (0) RLS is actually on
select tests.rls_enabled('public', 'services');

-- seed two tenants + a clinic user in tenant A (service-role / definer context)
-- ...insert tenants A,B; create user; insert membership(user_A, tenant_A);
--    insert services rows for A (published+draft) and B (published)...

select tests.create_supabase_user('a-owner@test.com');

-- (a) user A reads/writes A's rows
select tests.authenticate_as('a-owner@test.com');
select isnt_empty(
  $$ select 1 from public.services where tenant_id = '<tenant_A>' $$,
  'tenant A user sees tenant A rows'
);

-- (b) user A sees ZERO of tenant B's rows (the leak assertion)
select results_eq(
  $$ select count(*) from public.services where tenant_id = '<tenant_B>' $$,
  ARRAY[0::bigint],                       -- MUST be ::bigint, not 0
  'tenant A user sees ZERO of tenant B rows (cross-tenant leak)'
);

-- (c) anon sees only published, never drafts
select tests.clear_authentication();
select results_eq(
  $$ select count(*) from public.services where status <> 'published' $$,
  ARRAY[0::bigint],
  'anon sees only published rows'
);

-- (d) super-admin sees both tenants
-- ...insert platform_admins(super_user); authenticate_as super_user...
select results_eq(
  $$ select count(distinct tenant_id) from public.services $$,
  ARRAY[2::bigint],
  'platform admin sees both tenants'
);

select * from finish();
rollback;
```

### 4.3 CI ✅ — Docker is fine on the runner

The no-Docker preference applies to **prod hosting, not CI**. GitHub Actions runners have Docker; the official gate is three steps:

```yaml
- uses: actions/checkout@v4
- uses: supabase/setup-cli@v1
- run: supabase start # spins up local stack (Docker on the runner)
- run: supabase test db # runs the pgTAP suite
```

### 4.4 Optional defense-in-depth (JS integration) ✅

One thin Vitest/Jest test exercises the **real** `supabase-js → PostgREST → RLS` path (the pgTAP test bypasses PostgREST/JWT verification). A `service_role` client seeds two tenant owners via `auth.admin.createUser({ ..., email_confirm: true })`; two **anon-key** clients `signInWithPassword` and assert A can't read/write B + anon reads only published. ⚠️ No transaction rollback — tear down users/rows in `afterAll` (`auth.admin.deleteUser`). Treat pgTAP as the blocking gate, JS as smoke.

### 4.5 Test gotchas ✅

- `results_eq` is type-strict: counts are `bigint` → `ARRAY[0::bigint]`, not `ARRAY[0]`.
- Seeding via service-role bypasses RLS **by design** (so you can plant B's data). Never reuse the service-role client for the actual assertions — those must go through an impersonated/anon client or the test proves nothing.
- ⚠️ **Custom tenant claim caveat:** `tests.authenticate_as` injects `auth.uid()`/`sub` only. The §2 helpers read `tenant_id` from the **`memberships` table** (not a JWT claim), so this works as written. **If** R1 ever moves tenant resolution into a JWT `app_metadata.tenant_id` claim, the pgTAP test must set `request.jwt.claims` explicitly — the basejump helper may not do that out of the box.

## 5. `supabase gen types` + typed client factory in `packages/db`

### 5.1 Generate against the cloud project (no Docker) ✅

```bash
# package.json script inside packages/db
"gen:types": "supabase gen types typescript --project-id \"$SUPABASE_PROJECT_REF\" --schema public > src/database-generated.types.ts"
```

- ✅ Use `--project-id <ref>` (explicit ref, only auth needed — run `supabase login` / set `SUPABASE_ACCESS_TOKEN`) over `--linked`, so CI doesn't depend on a linked `config.toml`. Neither needs Docker; only `--local` does.
- ✅ Always pass `--schema public` explicitly (comma-separate extras) for deterministic output.
- ✅ Commit `database-generated.types.ts` — it's a build input, regenerated in CI to catch drift. It is **structure-only / no RLS awareness** (see §2.4).

### 5.2 jsonb override layer (spec §3 value-objects) ✅

✅ jsonb columns generate as the broad `Json` union. The spec's jsonb value-objects (`contact`, `address`, `opening_hours`, `social_links`, `cta`, Tiptap `body`/`description`/`answer`) must be narrowed via type-fest `MergeDeep`, with the **generated file imported under a different name** than the final `Database`:

```ts
// src/database.types.ts (hand-written)
import type { MergeDeep } from 'type-fest';
import type { Database as DatabaseGenerated } from './database-generated.types';
import type { z } from 'zod';
import type { contactSchema, openingHoursSchema /* ... */ } from './schemas'; // Zod = single source of truth

type Contact = z.infer<typeof contactSchema>;

export type Database = MergeDeep<
  DatabaseGenerated,
  {
    public: {
      Tables: {
        site_settings: {
          Row: { contact: Contact | null /* address, opening_hours, ... */ };
          Insert: { contact?: Contact | null };
          Update: { contact?: Contact | null };
        };
        // services.description (Tiptap JSON), faqs.answer, blog_posts.body, ...
      };
    };
  }
>;

export type { Tables, TablesInsert, TablesUpdate, Enums } from './database-generated.types';
```

✅ Derive override shapes from **Zod** (`z.infer`), not hand-written interfaces — the repo already uses Zod for forms, and the spec §3 mandates Zod at the admin write boundary, so compile-time override and runtime validation stay aligned from one source.

> ⚠️ **Gotcha:** if you regenerate over the _final_ filename you lose the override. Generate to `database-generated.types.ts`; re-export the merged `Database` from `database.types.ts`. Verify the emitted `Insert` shape for any default-bearing `uuid`/`text` id columns (CLI quirk `#2773` made them required in some versions).

### 5.3 Typed client factory — `@vetkit/*` conventions 🏠 + ✅

🏠 `tsconfig.json` extends `@vetkit/config-typescript/base.json` (Node package, **not** `nextjs`/`react-library`); 🏠 `eslint.config.mjs` imports from `@vetkit/config-eslint/base`. ✅ `strict` + `noUncheckedIndexedAccess` are on repo-wide, so `process.env.*` must be `!`-asserted or validated in the factory.

```ts
// src/client.ts
import { createClient as createSupabaseClient } from '@supabase/supabase-js';
import type { Database } from './database.types';

export function createAnonClient() {
  return createSupabaseClient<Database>(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY!,
  );
}
```

✅ `createClient<Database>(url, key)` propagates types to every `.from()/.select()/.insert()/.update()`. ✅ The publishable key carries the same low privilege as the legacy anon key, so RLS behaves identically.

> ⚠️ The `@supabase/ssr` `createBrowserClient`/`createServerClient` + `proxy.ts` machinery is **R2** (read-path / admin auth), out of scope for R1's `packages/db`. Listed as a dep so R2 doesn't re-touch the manifest. The public site has no session — R2 needs only the **read half** (a cookies-free server read client under the anon role).
